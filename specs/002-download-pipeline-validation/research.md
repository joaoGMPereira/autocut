## §1 — Real-time yt-dlp progress parsing

**Decision**: Parse yt-dlp `[download]` progress lines by reading subprocess stdout line-by-line using `cmd.StdoutPipe()` instead of `CombinedOutput()`.

**Rationale**: `CombinedOutput()` blocks until the process exits — no intermediate progress is possible. Reading via `StdoutPipe()` with a `bufio.Scanner` delivers each line as yt-dlp emits it. The `--newline` flag (already in `buildDownloadArgs`) forces yt-dlp to emit one progress update per line.

**Alternatives considered**:
- `--progress-template '{"pct":%(progress._percent_str)s,...}'` → not available in all yt-dlp versions; safer to parse the default `[download]` text line.
- External progress file + polling → adds filesystem coupling; rejected.

**yt-dlp progress line format** (with `--newline --no-colors`):
```
[download]  45.2% of  123.45MiB at    2.50MiB/s ETA 00:30
```

**Regex**:
```go
var progressRe = regexp.MustCompile(
    `\[download\]\s+([\d.]+)%.*?at\s+([\d.]+)(KiB|MiB|GiB)/s\s+ETA\s+(\d+):(\d+)`,
)
```

**Speed normalisation** (all to KB/s):
- `KiB/s` → multiply by 1
- `MiB/s` → multiply by 1024
- `GiB/s` → multiply by 1024×1024

**ETA to seconds**: `minutes*60 + seconds` from the `MM:SS` field.

**Streaming Executor design**:
```go
// StreamingExecutor replaces OSExecutor for download use.
type StreamingExecutor interface {
    RunWithProgress(ctx context.Context, name string, args []string,
        onLine func([]byte)) ([]byte, error)
}
```
- Starts cmd with `cmd.StdoutPipe()`; stderr captured separately via `cmd.StderrPipe()`
- `onLine` callback fires for each line of stdout; caller parses and emits SSE
- Uses `exec.CommandContext(ctx, ...)` for cancellation (see §3)
- Non-download commands (`ExtractMetadata`) can continue using `CombinedOutput()`

## §2 — Missing DB columns: video_title and duration_sec

**Decision**: Add migration v10 to `migrations.go`:
```sql
ALTER TABLE pipeline_runs ADD COLUMN video_title  TEXT    NOT NULL DEFAULT '';
ALTER TABLE pipeline_runs ADD COLUMN duration_sec INTEGER NOT NULL DEFAULT 0;
```

**Rationale**: The v9 schema (`migrateV9`) adds `video_path` and `transcript_path` but omits `video_title` and `duration_sec`. The spec's assumption ("no migration needed for these fields") is incorrect based on actual schema inspection. These fields are required by FR-007 (phase output contract) and SC-002 (measurable success criteria for downstream phases).

**Go model update** (`database/models.go`):
```go
type PipelineRun struct {
    // ... existing fields ...
    VideoPath    string `json:"video_path"`
    VideoTitle   string `json:"video_title"`    // NEW
    DurationSec  int64  `json:"duration_sec"`   // NEW
    TranscriptPath string `json:"transcript_path"`
    // ...
}
```

**Repo helper** (`pipeline_run_repo.go`):
```go
// SetDownloadResult persists all download phase outputs atomically.
func (r *PipelineRunRepo) SetDownloadResult(ctx context.Context, id int64,
    videoPath, videoTitle string, durationSec int64) error
```
Single UPDATE instead of three separate calls — reduces round-trips and ensures consistency.

**Alternatives considered**:
- Store title+duration only in SSE events (not DB) → violates FR-007 (phase output contract must be verifiable in DB); rejected.
- Separate `video_metadata` table → overkill for two scalar fields; rejected.

## §3 — Context-aware subprocess cancellation

**Decision**: Use `exec.CommandContext(ctx, name, args...)` for all yt-dlp subprocess invocations. Store a `cancelFunc` per active run ID in `pipeline.Service`, guarded by a `sync.Mutex`.

**Cancel flow**:
1. `Advance()` calls `context.WithCancel(context.Background())` → stores `cancelFunc` in `s.cancels[id]`
2. `runDownload()` receives this context; all `exec.CommandContext` calls use it
3. `Cancel()` calls `s.cancels[id]()` → `cmd.Cancel()` triggers `SIGKILL` on the subprocess → goroutine unblocks within OS scheduler latency (typically < 100 ms, well under the 3 s SLA)
4. `Cancel()` also calls `s.repo.Cancel()` to update DB state
5. `runDownload()` detects `ctx.Err() != nil` after `RunWithProgress` returns and skips further work

**Mutex requirement**: `s.cancels` map is read/written from multiple goroutines (Advance goroutine writes, HTTP Cancel handler reads). Use `sync.Mutex`.

**Cleanup**: `runDownload()` defers `delete(s.cancels, id)` (under lock) to avoid leaking cancel funcs for completed runs.

**Alternatives considered**:
- `cmd.Process.Kill()` directly → not accessible from cancel handler without storing the process; complicates the design vs. context propagation.
- Channel-based cancel signal → re-inventing context; rejected.

## §4 — URL validation before download attempt

**Decision**: Validate URL in `pipeline.Service.Advance()` before calling `repo.StartExecution()`. Reject if: not parseable as URL, scheme is not `http`/`https`, or host doesn't match a supported domain.

**Supported domains** (initial set, matches existing `isTwitch` logic):
```go
var supportedHosts = []string{
    "youtube.com", "www.youtube.com",
    "youtu.be",
    "twitch.tv", "www.twitch.tv",
    "clips.twitch.tv",
    "m.youtube.com",
}
```

**Validation function**:
```go
func validateURL(rawURL string) error {
    u, err := url.Parse(rawURL)
    if err != nil || u.Host == "" {
        return fmt.Errorf("invalid URL: %q", rawURL)
    }
    if u.Scheme != "http" && u.Scheme != "https" {
        return fmt.Errorf("URL scheme must be http or https, got %q", u.Scheme)
    }
    for _, h := range supportedHosts {
        if u.Host == h {
            return nil
        }
    }
    return fmt.Errorf("unsupported platform: %q (supported: YouTube, Twitch)", u.Host)
}
```

Returns a user-readable error surfaced as HTTP 400 by the handler — satisfies FR-010.

## §6 — Spec assumption correction: video_title in SSE contract

**Finding**: The spec's Key Entities section lists `video_title` as a `PipelineRun` field. The `video_info` SSE event already emits `title` and `thumbnail_url`. After migration v10 adds `video_title` to the DB, `runDownload` must call `SetDownloadResult` with `info.Title` so the field is persisted, not just broadcast via SSE.

`thumbnail_url` is intentionally **not** stored in the DB (not needed by downstream phases; already delivered via SSE `video_info`).
